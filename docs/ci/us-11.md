# US 11 — Paquets NuGet restaurés depuis Artifactory

**Cible** : le POC (int-poc), runner `cicd-int-poc` installé. Rien n'est fait sur l'intégration (int) avant la validation sur le POC.

**Contexte** : le build restaure aujourd'hui les paquets NuGet depuis le dossier `nugets` du dépôt (environ 580 Mo d'archive par build). Les essais du 24/11 ont montré qu'avec le **compte de build** (`usr-<kear_uid>`), Artifactory fournit tous les paquets publics ; seuls les paquets internes `SocGen.ApiBank.*` manquent et restent dans `nugets\socgen` (voir `src/scripts/devops/artifactory.md`, § 6).

Par ailleurs, le build du 24/11 a réussi alors que les paquets publics avaient été retirés de l'archive : la restauration avait trouvé tous les paquets dans le cache NuGet de la machine du runner. Un build ne prouvait donc pas que les sources de `nuget.config` suffisaient.

**Décisions** :

- `nuget.config` déclare deux sources : Artifactory (`ArtifactoryV2`) et `nugets\socgen` (`OfflineSocGen`). Les identifiants Artifactory sont lus dans deux variables d'environnement, jamais écrits dans le fichier.
- Le compte de build sert à la restauration comme au push : le runner tire le compte et le jeton de la variable GitLab existante `ARTIFACTORY_API_KEY` (`<compte>:<jeton>`). Pas de nouvelle variable GitLab.
- Chaque build et chaque package restaurent dans un dossier propre, sous les sources (`D:\ci\build\.nuget`), vidé à chaque commit : plus de dépendance au cache de la machine. Contrepartie : la restauration télécharge tous les paquets à chaque build (environ 1 min 30).

## Code

Le code de chaque fichier est dans [`us-11-scripts.md`](us-11-scripts.md) (une section par fichier) :

| Fichier | Changement |
|---|---|
| `src/scripts/devops/cicd/ci/cicd-int-poc.ps1` | version installée sur le POC, plus : lit `ARTIFACTORY_API_KEY`, la découpe en compte et jeton, et les transmet au build et au package sous `ARTIFACTORY_BUILD_USERNAME` et `ARTIFACTORY_BUILD_TOKEN` (environnement du processus, posé juste avant le lancement et retiré juste après). Chaque étape ne reçoit que ses propres identifiants : la clé de push n'est transmise qu'au push. Une clé absente ou mal formée est une erreur du runner : statut « échoué », commit repris au passage suivant |
| `src/scripts/devops/cicd/ci/cicd-int-poc.psd1` | deux clés en plus : `BuildUsernameVariable`, `BuildTokenVariable` |
| `src/scripts/devops/int/build.ps1` | paquets restaurés dans `<sources>\.nuget\packages` (`NUGET_PACKAGES`), cache HTTP dans `<sources>\.nuget\http-cache` ; le journal du build affiche le dossier |
| `src/scripts/devops/int/package.ps1` | idem |
| `src/scripts/devops/int/push-artifactory.ps1` | en cas d'échec, piste adaptée au code reçu (401, 403, 409) au lieu de l'astuce du conflit 409 affichée dans tous les cas |

`src/backend/nuget.config` :

```xml
<?xml version="1.0" encoding="utf-8"?>
<configuration>
  <packageSources>
    <clear />
    <add key="ArtifactoryV2" value="https://<artifactory>/artifactory/api/nuget/nuget-virtual-<kear_uid>" />
    <add key="OfflineSocGen" value="..\..\nugets\socgen" />
  </packageSources>
  <packageSourceCredentials>
    <ArtifactoryV2>
      <add key="Username" value="%ARTIFACTORY_BUILD_USERNAME%" />
      <add key="ClearTextPassword" value="%ARTIFACTORY_BUILD_TOKEN%" />
    </ArtifactoryV2>
  </packageSourceCredentials>
</configuration>
```

Sur un poste de développeur, chaque développeur crée une fois les deux variables d'environnement avec **ses propres** identifiants Artifactory (ceux qu'il saisissait dans Visual Studio) : voir « Texte à reporter dans le HOWTO », § 1.3. Le build ne modifie jamais les sources.

## Mise en place

L'ordre compte : le runner installé doit déjà transmettre les identifiants quand il construit la MR qui change `nuget.config`, sinon cette MR échoue (401).

### 1. Sur la machine du runner : nouvelle version du runner

1. Désactiver la tâche :

   ```powershell
   Disable-ScheduledTask -TaskName 'Styx.CicdIntPoc'
   ```

2. Dans `D:\ci\runner`, remplacer `cicd-int-poc.ps1` par le code de la section « cicd-int-poc.ps1 » de `us-11-scripts.md`. Dans `cicd-int-poc.psd1`, ajouter les deux clés à la fin (avant la dernière `}`) :

   ```powershell
       BuildUsernameVariable = 'ARTIFACTORY_BUILD_USERNAME'
       BuildTokenVariable    = 'ARTIFACTORY_BUILD_TOKEN'
   ```

3. Enregistrer les deux fichiers en UTF-8 avec BOM.
4. Lancer un passage à la main :

   ```powershell
   powershell -NoProfile -ExecutionPolicy Bypass -File D:\ci\runner\cicd-int-poc.ps1
   ```

   Résultat attendu : `Aucune MR à traiter (<n> ouverte(s)), main à jour.` Sans erreur sur la configuration.

5. Réactiver la tâche :

   ```powershell
   Enable-ScheduledTask -TaskName 'Styx.CicdIntPoc'
   ```

Cette version reste compatible avec l'ancien `nuget.config` : les variables transmises sont simplement ignorées.

### 2. Dans le dépôt : une MR

Sur une branche :

1. les trois scripts `int/` du tableau « Code », copiés depuis `us-11-scripts.md` ;
2. `src/backend/nuget.config` ci-dessus, **sans aucun identifiant en clair** ;
3. la suppression des paquets publics de `nugets/` (seul `nugets/socgen` reste) :

   ```bash
   git add -A nugets
   ```

   ```bash
   git status --short nugets
   ```

   Résultat attendu : des lignes `D` pour les paquets publics, aucune sous `nugets/socgen`.

4. `src/scripts/devops/artifactory.md`.

Pousser et créer la MR.

## Vérifications

1. **Build de la MR** : statut `ci-int` « réussi ». Dans le journal du build :
   - `Paquets NuGet : D:\ci\build\.nuget\packages` ;
   - une restauration nettement plus longue qu'avant (téléchargement des paquets).
2. **Taille de l'archive** : le journal du runner indique `Archive reçue` très inférieure à 578 Mo.
3. **Publication** : après la fusion, `cd-int` « réussi » et nouvelle version sur Artifactory.
4. **Aucun identifiant dans les journaux** : rechercher les premiers caractères du jeton dans `D:\ci\runner\logs` et `D:\ci\runner\builds` ne donne rien.
5. **Restauration réelle** : le dossier `D:\ci\build\.nuget\packages` existe après un build et contient les paquets.

**Fini quand** : le build et la publication passent sans les paquets publics dans le dépôt et sans le cache de la machine.

**Point à confirmer au premier build** : NuGet remplace bien `%ARTIFACTORY_BUILD_USERNAME%` et `%ARTIFACTORY_BUILD_TOKEN%` dans `packageSourceCredentials`. En cas de 401 sur la restauration, c'est la première chose à vérifier.

### Texte à reporter dans le HOWTO

Constaté sur le POC le 25/11 : un `nuget.config` sans la section `<packageSourceCredentials>` fait échouer la restauration en 401 sur tous les projets, alors que le runner transmet bien les identifiants. Une fois cette section ajoutée, le build passe (NuGet remplace bien les `%VAR%`).

**§ 1.3**, après la ligne sur `nuget.config` :

> - `nuget.config` contient aussi la section `<packageSourceCredentials>` pour Artifactory, avec `%ARTIFACTORY_BUILD_USERNAME%` et `%ARTIFACTORY_BUILD_TOKEN%` à la place du compte et du jeton : le runner remplit ces deux variables à chaque build. Aucun identifiant n'est écrit en clair dans ce fichier. Sans cette section, Artifactory refuse la restauration (401).

**§ 1.3**, nouveau paragraphe, avant la commande de vérification (qui est remplacée par celle de l'étape « Pour vérifier ») :

> **Sur un poste de développeur (une seule fois)**
>
> Le fichier `nuget.config` du dépôt lit les identifiants Artifactory dans deux variables d'environnement. Chaque développeur les crée avec **son propre** compte Artifactory et son jeton, ceux qu'il saisissait jusqu'ici dans Visual Studio.
>
> 1. Ouvrir une fenêtre PowerShell.
> 2. Enregistrer le compte :
>    ```powershell
>    [Environment]::SetEnvironmentVariable('ARTIFACTORY_BUILD_USERNAME', '<votre compte Artifactory>', 'User')
>    ```
> 3. Enregistrer le jeton, à coller quand il est demandé (il ne s'affiche pas dans la commande) :
>    ```powershell
>    [Environment]::SetEnvironmentVariable('ARTIFACTORY_BUILD_TOKEN', (Read-Host 'Jeton Artifactory'), 'User')
>    ```
> 4. Fermer puis rouvrir Visual Studio et toutes les fenêtres PowerShell : les variables ne sont lues qu'à leur ouverture.
>
> Pour vérifier, dans une **nouvelle** fenêtre, depuis `src\backend` :
> ```powershell
> dotnet restore --force --no-cache --packages "$env:TEMP\nuget-test"
> ```
> Vous devez voir la restauration se terminer sans erreur `NU1301`, après le téléchargement des paquets. Supprimer ensuite le dossier `$env:TEMP\nuget-test`.

**§ 6**, nouvelle ligne du tableau (la ligne `NU1301` existante reste pour le cas réseau) :

> | `Build échoué` avec `NU1301` et `401` ou `403` dans le journal | Artifactory refuse la connexion : vérifier la section `<packageSourceCredentials>` de `nuget.config` (étape 1.3), puis le compte et le jeton de `ARTIFACTORY_API_KEY` (étape 2.3) |

**Constat du 27/11 (poste de développeur)** : sans les deux variables, la restauration échoue (403). Un « Nettoyer » dans Visual Studio suivi de `dotnet restore --no-cache` ne le montre pas : les paquets déjà présents sur le poste suffisent et Artifactory n'est pas contacté. Avec les variables, la restauration complète (`--force --packages` vers un dossier vide) et la regénération dans Visual Studio après « Effacer tout le stockage NuGet » réussissent : Visual Studio remplace bien les `%VAR%`.
